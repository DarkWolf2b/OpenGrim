- Java shell: `analysis/decompiled/payload-named/sixtwo/gb.java` (CFR; all bodies `native`; implements `sixtwo.ga`; statics `YRQDX` `ArrayList`, `aMmNt` `Vector`, `idqOu` `int[]`, `EYSuF` `long[]`, `saIRC`/`GyBiN`/`Oefhm` `int`, `anmuy` `Object`). No `gb$*.java` inner classes exist.

- Sibling `ga` implementor: `analysis/decompiled/payload-named/sixtwo/fZ.java` — hardcoded `int[64] ojvoM` table (64 literal values, `fZ.java:22–82`), registers itself via `gb.aYU(this)` in its constructor.
- Consumer side (GUI shell): `analysis/decompiled/payload-named/sixtwo/av.java` — abstract `Screen` base of the GUI; its `<clinit>` calls `gb.aYR(5327485615965762991L, -6615214864910727710L, MethodHandles.lookup().lookupClass()).a(37594205416973L)` (`av.java:68`); the same `aYR(...).a(...)` idiom appears at hundreds of call sites across `sixtwo/*.java` (every module, screen and helper class).
- Decrypted-constant dump: `analysis/decrypted/full-dump.jsonl` — **zero** entries with `"class":"sixtwo.gb"` (gb runs no `invokedynamic` constant bootstrap of the `fF.aTe` style; its pool is decrypted natively via `BLOB_DECRYPTOR`).
- `analysis/specs/coverage-matrix.tsv` — no `gb` row (it is not a module).
- Yarn mapping: not needed for gb itself — no MC class/method reference appears anywhere in gb's pool windows (see below).

**Classification correction (important).** `gb` is **not** the visual ClickGUI/HUD renderer. Its handlers contain **no** `DrawContext`/rendering references, no ARGB constants, no layout constants. `gb` is the **native constant-key registry**: the `ga`-typed native anchor that every class bootstraps its opaque key material through (`aYR(J,J,Class).a(J) → long`), plus the bookkeeping state (map/list/vector/int[64]/long[]) that supports it. All *visual* GUI behavior lives in the Java shell classes that *surround* gb — abstract `Screen` base `av` and subclasses `bz`, `bl`, `bD`, `c`, with the `lC` DrawContext wrapper — summarized in "GUI architecture" below and marked by origin throughout. Faithfulness rule applied: everything not visible in gb's handlers is listed under *Unrecovered*, not invented.

**Runtime architecture constraint (governs everything below).** Same pattern as the fC spec: every handler stub performs `BLOB_DECRYPTOR` on a shared constant-pool window, then `JNI->ExceptionCheck`, then dispatches through an indirect jumptable into the payload runtime loop (`FUN_190ddce00`, `FUN_190ddfc90`, `FUN_190dd72e0`, `FUN_190dd9df0` — runtime helpers, not analyzed). Continuation blocks are (a) single-JNI-op micro-trampolines tail-jumping via `(*_DAT_xxx)()`, (b) opaque-constant "whiteout" arithmetic — heavy mixing via `func_0x00018a53a080` / `func_0x00018a704ef0` / `func_0x00018a73c5a0` over `_DAT_18325xxxx`/`_DAT_183256xxx` state, with SWAR popcount idioms (`0x5555555555555555`, `0x3333333333333333`, `0x0f0f0f0f0f0f0f0f`, `0x101010101010101`) and the ubiquitous salt `0x84222325` / mask constants `0x7bdddcda`, `0x8422231d`, `0x84222365` — anti-trace noise, not GUI math, and (c) `halt_baddata` jumptable fragments where control flow is lost. `rdtsc` does **not** appear in this corpus. Exact branch/arithmetic order inside handlers is therefore not recoverable; the recoverable facts are the pool inventories, JNI call sequences, loop guards, and shared-structure types.

## GUI architecture

*(What gb's handlers show, then what the Java shell shows — origins labeled.)*

- **gb's own role (handlers).** gb is a per-class native state node. A consumer class calls `gb.aYR(long k1, long k2, Class<?> lookupClass)` (`[18a52b750]`), which returns a `ga` instance keyed by the calling class; `ga.a(long seed)` (`[18a73c630]`) derives the consumer's opaque `long` key (`oVYdO` in `av`, `smakX` in `az`, `wQvIR` in `aF`, …). That key is then XOR-folded into every guarded Java-side literal (`av.java:59` `long l2 = oVYdO ^ 0x1B5D73AB471DL;`) and feeds the DES key schedule in `av.<clinit>` (`av.java:70–88`: `Cipher.getInstance("DES/CBC/NoPadding")`, key = bytes of `oVYdO ^ 0x7B5CA3A0E4D4L`, decrypts fixed long `-3729010028508391083L` → `myUnc`). In other words gb supplies the constants that deobfuscate the GUI shell's own logic; it does not draw anything.
- **Registry machinery (from `aYR`'s pool window `POOL[0x15431,0x355]`, in pool order):** `sixtwo/fZ` (+ `Lsixtwo/fZ;`), `aYJ (Lsixtwo/ga;Lsixtwo/ga;)Lsixtwo/ga;`, `java/util/concurrent/ConcurrentHashMap`, `aYN`, `aYV (Lsixtwo/fZ;)V`, `sixtwo/ga`, `aYP (Lsixtwo/ga;)V`, `aYS (J)Lsixtwo/ga;`, `idqOu`, `ojvoM` (fZ's `int[64]`), `System.arraycopy`, `identityHashCode`, `anmuy`, `aYH`, `aYT (J)Lsixtwo/ga;`, `aYI`, `aMmNt Ljava/util/Vector;`, `Oefhm`, `EYSuF`, `aYY (JII[I[J)J`, `saIRC`, `YRQDX Ljava/util/ArrayList;`, `GyBiN`, `aYZ`. Interpretation: a `ConcurrentHashMap` (per-instance in fZ: `noZXa`, and static equivalents behind gb) keyed by `identityHashCode`, with `Vector aMmNt` + `ArrayList YRQDX` as ordered node lists, `int[] idqOu` / `long[] EYSuF` as the compact native-side state snapshots exposed through `b()[I` / `aYY`, and the `aYH–aYZ` family as the mutate/notify ops. `System.arraycopy` copies table data between `idqOu`/`EYSuF` and node arrays (fZ's `ojvoM`).
- **Screen classes (Java shell, not gb).** `av extends Screen implements cs` — abstract base of the GUI screens; concrete subclasses `bz` (2412 lines — the largest screen, main ClickGUI), `bl`, `bD`, `c` (all in `sixtwo/`). `av` holds `rk Weytw` (animation timer) and `boolean VWsmm` (`closing()`, default `true`); `shouldPause()` is always `false`; `renderBackground` calls `renderPanoramaBackground` only when `client.world == null` (i.e. panorama behind GUI when not in-game) (`av.java:382–409`).
- **Open/close flow (Java shell).** `av.sf()` returns `0.5f + 0.5f * Weytw.dhj()` — the open/close animation progress driven by `rk` (a timer with `dht(long)` duration and `dhv(float)` target setters, `rk.java:140–145`). No native open/close call is visible in the Java shell; screen open/close goes through vanilla `Screen` lifecycle.
- **Input event routing (Java shell, `av.java:243–449`).** Every vanilla handler is overridden `final` and re-routes through the `cs` interface methods with **screen-space coordinates from `rm.dis()`** (the scale-aware mouse position), never the raw vanilla args: `mouseClicked(Click, boolean)` → `onMouseClicked(rm.dis().x, rm.dis().y, mA.cmN(click.button()))`; `mouseReleased` → `onMouseReleased(x, y, button)`; `mouseDragged(Click, dx, dy)` → `onMouseDragged(x, y, button, dx, dy)`; `mouseScrolled` → `onMouseScrolled(x, y, verticalAmount)`; `keyPressed(KeyInput)` → `onKeyPressed(key, scancode, modifiers)`; `charTyped(CharInput)` → `onCharTyped((char) input.codepoint())`. If the routed handler consumes the event, the vanilla super call is skipped. `mA.cmN(int)` normalizes the button id; `si()` re-presses the client's keybindings (`iX.HpSlL`) from `rr.diW(key.getCode())` — restores gameplay keybinds while a GUI screen is open.
- **Scale factor handling (Java shell).** `av.sh()` computes the GUI scale: with `n()` = the abstract desired GUI viewport `Vec2f` (per-screen), `d = min(window.x / n().x, window.y / n().y)` (`window` = `rm.dip()`, framebuffer size `rm.java:439`), then `MathHelper.clamp(d, 0.5, 2.0)`; returns default `2.0` when the viewport is degenerate (`av.java:141–221`). `av.render` applies it via `rm.dil(sh())` before rendering and `rm.dim()` after (`av.java:416–421`) — a save/apply/restore of a global scale+mouse transform in `rm`.
- **Render frame (Java shell).** `av.render`: set scale (`rm.dil(sh())`) → get scaled mouse `rm.dis()` → build render context `lC.ccP(context, mouse.x, mouse.y, deltaTicks)` → `this.m(lC2)` (abstract per-screen draw) → `finally { lC2.ccR(); rm.dim(); }`. `lC` wraps `DrawContext` and uses `Matrix3x2fStack`, `Matrix4f`, `GpuTextureView`, `AbstractTexture`, `Identifier`, `Text`, `Vec2f`, `AbstractClientPlayerEntity`, `PlayerEntityModel`, `EntityRenderState`, `LivingEntity`, `ItemStack` (`lC.java` imports) — i.e. the frame has a matrix stack, texture/image draws, and a 3D-player render path (target HUD-style entity preview) available through `lC`.

## Layout math

**From gb's handlers: none recoverable.** gb exposes no layout constants; the only size-like constants in the corpus are registry/plumbing values (`0x40` = 64 in `aZc`, `0x38`/`0x3f` throw-argument words in `aYR`'s continuation blocks). All panel positions, column arrangement, gaps and scroll math for the ClickGUI live in the screens (`bz`, `bl`, `bD`, `c`) and are executed as VM-interpreted natives in *those* classes' handlers — out of scope for this file and not present in `sixtwo_gb.c`. **Do not copy any layout numbers into a reimplementation from this spec.**

Java-shell facts only (no pixel constants): the render viewport is the framebuffer (`rm.java:439`), scaled by `sh()` (clamp[min(ratio), 0.5, 2.0], default 2.0); screens declare their desired viewport via abstract `Vec2f n()`; scrolling enters via `onMouseScrolled` with the raw `verticalAmount`.

## Colors and fonts

**Unrecovered — zero ARGB constants and zero font references exist in gb's handler corpus.** Checked exhaustively: the corpus's recurring 32-bit constants (`0x84222325`, `0x7bdddcda`, `0x8422231d`, `0x84222365`, `0x958a7e68`, `0xf896dcd2`, `0x7f1dd4fa`, `0xfe56e3dd`, `0xfb3ff7df`, `0xa6a08c60`, `0x750b8be7`, `0x69d5bb3d`, `0x64618186`, …) are whiteout-mixing salts (they appear exclusively inside `func_0x0001…` mixing chains over `_DAT_1832…` state), not colors; there is no `0xAARRGGBB`-shaped constant, no `Color`/`ShaderProgram`/`Identifier` reference, and no font-resource string in either POOL window. The decrypted dump has no `sixtwo.gb` entries at all, and no GUI color/font/token strings were found associated with gb. The GUI's palette and font renderer are native to the screen classes and are **not recoverable from this file**.

## Rendering pipeline

**From gb's handlers: nothing.** gb never touches `DrawContext`, matrices, buffers or textures; its only "array" work is the int/long state plumbing described under Per-handler semantics. The render pipeline facts attributable to the *Java shell* (origin: `av`/`lC`): per frame — apply scale → wrap `DrawContext` in `lC` (matrix `3x2f` stack) → `m(lC)` draws the screen → pop/restore. `renderBackground` draws the vanilla panorama only when not in a world; no blur, rounded-rect or gradient primitive is visible at the `av` layer (any such primitives are inside `bz`/`lC`/`lC`-drawn widgets, native and unrecovered here). Any ordering claims beyond this would be speculation — see Unrecovered.

## Interaction

**From gb's handlers: none.** gb has no mouse/keyboard/binding logic. The interaction contract the Java shell establishes for the (native) screen bodies, which a clean-room implementation must reproduce:

- Hit-testing uses **scaled screen-space coordinates**: `rm.dis()` (scale-corrected mouse) against the screen's own coordinate system laid out under `sh()` scale.
- Button ids are normalized through `mA.cmN(int)` (`mA` = button enum, 368 lines); drag events carry `offsetX/offsetY` deltas from vanilla `mouseDragged`.
- The `cs` handler set is: `onMouseClicked`, `onMouseReleased`, `onMouseDragged`, `onMouseScrolled`, `onKeyPressed`, `onCharTyped` — each may consume the event (then vanilla super is skipped) or pass it through.
- While a GUI screen is open, gameplay keybindings are force-synced through `si()` (`keyBinding.setPressed(rr.diW(key.getCode()))`) so module keybinds do not leak into the world.
- Bind capture, slider drag math, search/filter: **unrecovered** (inside `bz`/`bl`/`bD`/`c` native bodies).

## HUD elements

**None shown by gb's handlers.** gb draws no HUD. `lC`'s import surface (`lC.java`) shows the render toolkit available to HUD widgets — including a full `PlayerEntityModel`/`EntityRenderState`/`AbstractClientPlayerEntity` path (consistent with a target-HUD player preview), item-stack and text draws, and custom textures (`Identifier`/`AbstractTexture`/`GpuTextureView`) — and the sibling branch history confirms Target-HUD (`fX Interface`, 0 natives — pure Java interface) and similar widgets exist, but the watermark/arraylist/target-HUD draw bodies are **not in this corpus**. No ordering, no animation curves, no pixel constants.

## Per-handler semantics

All handlers share the stub prologue: `BLOB_DECRYPTOR(env, poolBase, off, len)` → `JNI->ExceptionCheck` → jumptable dispatch. Only distinguishing behavior is listed.

- **`_bab653dcf48cf5170082af05b37ffda0()V` — static init `[18a702c70]`.** Infra. Decrypts POOL[0xa49,0x29] (`Ljava/lang/invoke/MethodHandle; | sixtwo/gb`), `ExceptionCheck`, jumptable `[18a702cf9]`. Boots the class's VM state (seeds statics `idqOu`/`EYSuF`/lists from native tables; Java shell `gb.java:24–27` pairs it with `Loader.doInit`).
- **`a(J)J` — key derivation (`ga.a`) `[18a73c630]`.** Behavior-critical but opaque: decryptor over POOL[0xa49,0x29], jumptable `[18a73c69b]`. Contract from call sites: maps the instance's native handle + caller's seed long to the class's opaque key long (e.g. `gb.aYR(k1,k2,Class).a(seed)`).
- **`a(ga)V` — link/set (`ga.a(ga)`) `[18a73d2f0]`.** Opens with `JNI->IsSameObject` `[18a73d31d]` — identity-guarded store into the registry node (consistent with: if the new node is the same object, no-op / else replace).
- **`aYQ()Object` — get registry object `[18a52b5c0]`.** Decryptor + jumptable `[18a52b606]`; continuation `GetStaticObjectField` tail `[18a52b681]`. Returns the bootstrap object (Java shell types it `Object`); unrecovered which static it returns.
- **`aYR(JJObject)ga` — registry lookup/create `[18a52b750]`.** The largest pool window, `POOL[0x15431,0x355]` — full inventory in "GUI architecture". Recoverable continuation ops: `CallStaticObjectMethodA` `[18a52ba49]`, `CallBooleanMethodA` `[18a52bcd4]` (map/list containment check), `GetStaticObjectField` `[18a52bb80]`, `CallNonvirtualLongMethodA` `[18a52cc19]` (the `identityHashCode` call of the pool), `ThrowNew` guards `[18a52bff4]` `[18a52c0b6]` `[18a52c419]` (arg-validation throws; stack words `0x38`/`0x3f` at `[18a52c27e]`), `arraycopy`/`Vector`/`ArrayList` construction per pool order. Behavior: `aYR(k1, k2, lookupClass)` → resolve or create the `ga` node for `lookupClass`, keyed by `identityHashCode`, initializing its `int[]`/`long[]` tables via `arraycopy` from the shared statics.
- **`aYS(J)ga` — node by handle `[18a7019f0]`** and **`aYT(J)ga` `[18a704f80]`.** Handle → `ga` lookup pair (get vs. peek semantics; both decryptor + jumptable only, `[18a701a4b]` / `[18a704fcd]`). Which of the two tolerates a missing node is unrecovered.
- **`aYU(fZ)V` `[18a705190]` / `aYV(fZ)V` `[18a705750]` — fZ lifecycle.** Register (`aYU`, called from `fZ`'s constructor, `fZ.java:84`) and its update/attach counterpart (`aYV`, in `aYR`'s pool). Both decryptor + jumptable only.
- **`aYW(I)J` — int-indexed constant derivation `[18a52c7f0]`.** One of the two fully-visible whiteout bodies: multiply-add chain over 64×64 constant grids (`_UNK_1817abe50…f10`, `_UNK_1817ac440…d70`, `_UNK_1817ac830…d80`, …) with SWAR popcounts, salts `0x84222325`/`0x7bdddcda`, rotates `<<0x11 ^ x` / `x*0x2000 | x>>0x33`. Pure anti-trace derivation of a long from an int index; no Java-side call sites (VM-internal).
- **`aYX(II)J` `[18a52ccd0]`.** Single null-guard jumptable `[18a52ccf9]`; private, VM-internal.
- **`aYY(JII[I[J)J` — native state snapshot `[18a52d1c0]`.** The third handler in the `aYR` pool. Continuations: `GetArrayLength` + `0 < len` guard `[18a52d2b3]`, loop compare `idx < len` `[18a52d41b]`, `GetPrimitiveArrayCritical` `[18a52d592]` (pins the `int[]`/`long[]`), `CallStaticLongMethodA` `[18a52d0e8]`. Behavior: serialize/pack node state between the JVM arrays (`idqOu`, `EYSuF`) and native memory under a critical section. The `aZa`/`aZb` pair below consumes/produces the same lists.
- **`aYZ()V` `[18a53a110]`** — registry flush/reset tick (decryptor + jumptable `[18a53a16a]`).
- **`aZa(I,I,ArrayList,ArrayList,I)V` `[18a53aaa0]`.** Paired-list walk: entry guard `param_3 < param_4` `[18a53aad8]`, loop compare `[18a53ae4c]` (`R12D < EBP`), `CallStaticVoidMethodA` `[18a53aef6]`. Two `ArrayList`s (`YRQDX`-style) indexed by two ints up to a limit; per-element static callback. Registry bookkeeping — **not** a render loop.
- **`aZb(I,I,I,ArrayList,ArrayList)V` `[18a53b130]`.** Twin walk: guard `param_5 < param_3` `[18a53b1bf]`, loop `[18a53b1c2]`, `CallObjectMethodA` `[18a53bd24]` (element fetch), `IsInstanceOf` `[18a53bdab]` (element type check). Same data, element-wise with type filter.
- **`aZc()V` — table allocation `[18a53cd80]`.** `JNI->NewIntArray(env, 0x40)` then `GetArrayLength` ≥ 1 check `[18a53cdf5]`; continuation `SetIntArrayRegion` + `GetArrayLength ≥ 2` `[18a53ce4e]` (writes a two-int header into the fresh array). Allocates/refreshes the shared 64-int table — the static `idqOu` counterpart of fZ's literal `int[64] ojvoM` (`fZ.java:22–82`). **This 64 is the only meaningful numeric constant in the corpus** and is registry state size, not GUI geometry.
- **`b(J)V` — set handle (`ga.b(long)`) `[18a73d100]`.** Guard `[18a73d125]`, `SetLongField` + `ExceptionCheck` `[18a73d23b]` — stores the long handle into the instance's `fypFy` field.
- **`b()[I` — get table (`ga.b`) `[18a52c5f0]`.** Guard `[18a52c610]`, `ThrowNew` on failure `[18a52c64c]`, `GetObjectField` `[18a52c726]` — returns the static `idqOu` int array.
- **`b(ga)Z` — identity test (`ga.b(ga)`) `[18a52c1c0]`.** `JNI->IsSameObject` `[18a52c1f2]`; reference-identity equality.
- **`equals(Object)Z` `[18a52bdb0]`.** `JNI->IsSameObject` `[18a52bde2]` — identity semantics, no structural comparison.
- **`hashCode()I` `[18a73d8d0]`.** Decryptor + jumptable `[18a73d927]`; `CallNonvirtualLongMethodA` `[18a73d9eb]` (identityHashCode) truncated to `int` — identity hash again.

## Unrecovered / uncertain

- **Every visual constant.** No ARGB colors, panel widths/heights, paddings, gaps, corner radii, font names/sizes, animation durations or easing curves exist in gb's handler corpus. The only concrete numbers are registry plumbing (`0x40` table size, `0x38`/`0x3f` throw words). **The ClickGUI's layout and palette are unknown from this file.**
- **Which of `aYS`/`aYT` tolerates absent nodes; what `aYQ` returns; the exact key schedule mapping `aYR(k1,k2,Class).a(seed)` → key long.** The derivation is whiteout-arithmetized; only the call-site contract is proven.
- **The bodies of `aZa`/`aZb`'s static callback and the meaning of the paired `ArrayList`s** — inferred as registry bookkeeping from types and call shapes; the alternative (a hidden GUI data structure) cannot be excluded from this corpus alone.
- **Concrete screen bodies** (`bz`, `bl`, `bD`, `c`, `lC` widget drawing): these classes' own native handlers are the correct evidence base for layout/colors/render order and are out of scope here; their CFR Java shells are key-scrambled (DES/XOR via `oVYdO`-style keys) and yield no direct constants.
- **Whether gb participates in anti-debug beyond the whiteout mixing** — no `rdtsc`, `IsDebuggerPresent` or thread-check block appears in this stitched corpus, but the unresolved jumptables (`0x1867xxx`, `0x1868xxx`, `0x1869xxx`, `0xa33f407`) hide the full dispatch graph, so absence is not proven.
