## 2. Root cause

`ChinaHat.drawCone` requested **two** buffers from the same
`VertexConsumerProvider.Immediate` before writing either of them (old
`ChinaHat.java:142-143`):

```java
VertexConsumer fan   = consumers.getBuffer(RenderLayers.debugFilledBox());
VertexConsumer lines = consumers.getBuffer(RenderLayers.lines());
...
fan.vertex(entry, ax, ay, az)...      // old line 158 — throws here
```

`VertexConsumerProvider.Immediate` (yarn jar, `javap -c`) holds **one** active
non-dedicated layer at a time:

* `getBuffer(layer)` returns the pending builder for a layer only while that layer
  is `currentLayer`; the map of dedicated allocators
  (`BufferBuilderStorage` → `entityVertexConsumers`) contains only textured/glint/
  waterMask/block-destruction layers — `debugFilledBox()` and `lines()` are **not**
  in it.
* When a different non-dedicated layer is requested, `getBuffer` calls
  `draw(currentLayer)` → `BufferBuilder.endNullable()` → `building = false`
  (`BufferBuilder` ctor sets `building = true`; `ensureBuilding()` throws
  `"Not building!"`).
* So `getBuffer(RenderLayers.lines())` ended the fill builder. The very next write
  to `fan` hit `ensureBuilding()` → `IllegalStateException: Not building!`.

The original has no such constraint: `ky.bSd` builds each pass in its own
`BufferAllocator`/`BufferBuilder` (TRIANGLE_FAN then DEBUG_LINE_STRIP) and submits
each via `lF.cfX(...)` (ky.java:103-193, 199-283) — two independent buffers.

**Why it became a hard crash instead of one printed error:** `EventBus.post` swallows
listener `Throwable`s and prints them (parity with `sixtwo.hH#bdV`, `EventBus.java:71-79`),
so the exception did *not* unwind the caller. `ChinaHat.onWorldRender` had already
pushed the shared `MatrixStack` (old line 98) and its `pop()` (old line 120) was
skipped by the throw. The Fabric `AFTER_ENTITIES` hook wraps the
`Immediate.drawCurrentLayer()` call that precedes `WorldRenderer.checkEmpty(matrices)`
(verified in the `javap` listing of the submission pass: `drawCurrentLayer()` then
`checkEmpty`), so the leaked push detonated one call later as
`IllegalStateException: Pose stack not empty`. Same failure shape as the 10:43.37
StorageEsp leak, but this time the leak was caused by a swallowed exception rather
than an early return.

## 3. Fix applied (`src/main/java/dev/opengrim/modules/render/ChinaHat.java`)

1. **`drawCone` — one pass per `getBuffer` (root cause).** The rim geometry and
   per-segment gradient are precomputed once (ky.java:104-134); pass 1 requests
   `debugFilledBox()` and writes all fan quads, pass 2 requests `lines()` and writes
   the rim strip. Every consumer is fully written before the next `getBuffer` call,
   so no builder can be ended under a live reference. Vertex stream is byte-identical
   to the previous port for both passes (same order, same colors, same alpha 40.0f).
2. **`onWorldRender` — `try/finally` around push/pop.** The pop now runs even when the
   render body throws (EventBus swallows the throwable, so the leak would otherwise
   still reach `checkEmpty`). Mirrors the fix pattern already used in `StorageEsp`
   (`StorageEsp.java:398-435`).
3. **Secondary 1:1 correction found while restructuring (same function).** The old
   closing line was `line(..., ax + prevX, by, az + prevZ, ax, by, az, closing)` with
   `closing = gradient(time, 0, ...)` — a spoke from the rim to the *center* of the
   cone, colored with segment 0. The original's closing vertex (ky.java:221) is
   `(-sin(0)*width, 0, cos(0)*width)` = the **angle-0 rim point again** (the strip
   already ends at 2π, so it is a zero-length segment) with the **last loop
   iteration's** color (`var10_9`, assigned from the final `jk.bDm(i)` at ky.java:209).
   Now emitted exactly like that: `line(..., rimX[SEGMENTS], rimZ[SEGMENTS] →
   rimX[0], rimZ[0], rimRgb[SEGMENTS])`. Removes a visible spoke the original never
   drew. No other geometry touched.

No guesses introduced; the `[G]`-labeled items already documented in the class
javadoc (segment count, gradient triangle constants, head-offset pose query) are
unchanged.

## 4. Same-class risk scan (buffer discipline)

Searched every non-GUI source file for methods containing 2+ `getBuffer(...)` calls
(script over brace-balanced method bodies):

| file | method | verdict |
|---|---|---|
| `modules/render/ChinaHat.java` | `drawCone` | **was broken — fixed** (now sequential) |
| `modules/render/Trails.java:210,222` | `renderPlayerTrail` | safe — quad consumer written out (211-220) before `linesTranslucent()` is requested |
| `modules/render/HealthIndicators.java:270,275` | `renderPlayerHearts` | safe — each buffer is passed inline into `drawHeartRows`, which writes immediately |
| `modules/render/PopChams.java:242,246` | `renderClone` | safe — the two calls are if/else alternatives |

All other render modules (`BlockEsp`, `StorageEsp`, `HoleEsp`, `EntityEsp`,
`FireworkSpots`, `LogoutSpots`, `SoundEsp`, `Trajectories`, `Nuker`, …) follow the
"helper does getBuffer + immediate write" shape, which is inherently safe against the
`currentLayer` flush. Cross-listener interleaving is safe too: `EventBus.post` runs
listeners sequentially and each completes its writes before the next starts.

## 5. Same-class risk scan (pose stack)

Script: for every `.push()` in non-GUI sources, take the text to its matching
`.pop()` and test for `finally` / early `return`:

* No remaining `push → return → pop` (early-return) cases — that class was already
  cleared (StorageEsp and peers gate before the push).
* **37 push sites still pop without `try/finally`**, so any throwable raised between
  push and pop (swallowed by `EventBus.post`) will still hard-crash the same way:
